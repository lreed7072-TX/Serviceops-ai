# Plan 03: Create qbo-types.ts — QBO entity type definitions

## Objective
Create a comprehensive TypeScript type definition file (`qbo-types.ts`) containing interfaces for all 18 QBO entity types plus common shared types (QboRef, QboAddress, QboLine, etc.). Migrate the existing inline `QboCustomer` and `QboInvoice` types out of `qbo-client.ts` into this new file, and re-export them from `qbo-client.ts` for backward compatibility. These types are pure interfaces with zero runtime cost and establish the complete type system for all 6 phases.

## must_haves
- [ ] `src/lib/qbo/qbo-types.ts` exists with all 18 entity types and 7+ common types defined as TypeScript `type` exports
- [ ] `qbo-client.ts` no longer contains inline `QboCustomer` or `QboInvoice` type definitions — it re-exports them from `qbo-types.ts`
- [ ] `npx tsc --noEmit` passes with zero new errors after the type migration

- The new `QboCustomer` adds `SyncToken: string` and `MetaData: QboMetaData` as required fields. This may cause issues where `qbo-client.ts` functions return `QboCustomer` but the QBO API response includes these fields naturally.
- If needed, make `SyncToken` and `MetaData` optional on the expanded types, OR use `Partial<QboCustomer>` in return type positions, OR keep `SyncToken` and `MetaData` as optional (`?`) since they are always present in QBO responses but not always needed by consumers.

The safest approach: In the `QboCustomer` definition in `qbo-types.ts`, make `SyncToken` and `MetaData` non-optional (they are always present in QBO API responses). The existing code that constructs `QboCustomer` payloads to POST will work because QBO ignores `SyncToken` on create and requires it on update (where it comes from the fetch-merge pattern).
